# Omni 语音模型选型（2026-11-15）

小型 Omni 可以作为本项目的实验方向：在 OpenI 接收音频并直接生成文字和语音，媒体服务器继续负责电话/WebRTC、重采样、播放、打断和连接清理。这里是官方资料核查及下一轮实验设计，**没有完成 Omni 权重加载、语音推理或一秒延迟验收**。现有三模型 provider 和配置继续保留。

## 候选与硬件

| 候选 | 已核实能力 | 对现有 A100 40GB 的判断 |
| --- | --- | --- |
| MiniCPM-o 4.5，9B 总参数 | 中英语音、可配置提示词和参考音色；流式音频输入/输出、全双工；官方提供 PyTorch 和 llama.cpp-omni 服务示例 | 优先测试。官方 PyTorch 服务要求至少 28GB 显存，A100 40GB 符合容量条件；并发、长上下文及实际首音另测 |
| Qwen2.5-Omni-3B | 音频输入、文字和语音输出；Thinker–Talker 架构 | 可作较小模型对照。官方 BF16 表的 18.38/22.43/28.22GB 对应 15/30/60 秒**视频**输入、FlashAttention 2 的理论下限，不能直接当作电话显存实测 |
| Qwen3-Omni-30B-A3B-Instruct | 音频输入、流式文字/语音输出；MoE | 不作为本轮省费首选。激活 3B 不代表只加载 3B；完整模型为 30B，官方 BF16 15 秒视频示例理论下限为 78.85GB。量化及其他引擎需分别验证，不能据此断言所有路径都无法在 40GB 运行 |

MiniCPM-o 4.5 的量化 llama.cpp-omni 路径，官方列出的 NVIDIA 门槛为 12GB 显存；不等于所有量化格式、上下文和并发都只用 12GB。先在已经验证可用的 A100 上测无损路径，达标后再用同一组问题对照低价显卡或量化，避免同时改变模型、引擎和硬件。

## 为什么优先核查真实流式服务

Omni 内部仍可能包含文字解码、语音 token 解码和声码器；参数较少、减少 HTTP 请求或模型宣称流式，都不保证停口后一秒内出声。

MiniCPM 官方 PyTorch 服务表中的 A100 全双工每单元约 0.9 秒、启用编译约 0.5 秒是**官方单元耗时**，不是本项目的停口到终端有效首音。该表还记录编译准备成本，不能隐藏首次编译、预热和实际网络开销。其模型评测中的 0.6 秒首 token 也不是首段有效语音。

Qwen2.5-Omni 官方说明普通 `vllm serve` 路径只支持 Thinker 的文字输出；语音需要专门的端到端实现，不能把标准 Chat Completions 接口配置好就称为可说话。语音输出还要求特定系统提示词；官方将角色定制放进预置对话的方案，需检查产品约束、金额、销售步骤和挂断要求能否稳定遵循。

MiniCPM-o 官方也列出全双工下可能读错字、混用中英文和能力不稳定的限制。对电话咨询，必须另测价格、车型/产品型号、地址和拒绝购买等具体语义。

## 下一轮实验边界

1. 先确认 OpenI 可挂载的完整权重或准备好经验证的镜像；锁定模型、远程代码和依赖版本。准备完成后才占用 GPU 做少量推理，语音组件采用国内镜像、断点续传和进度日志，允许最多两小时准备，避免短时限导致反复停止重建。
2. 复用现有测试问题和虚构产品资料，关闭思考；记录从用户讲话期间的分块输入、真实停口边界，到首段有效中文语音的全过程。完整输入一次提交、首 token、PCM 首包分别记录，不混成端到端结果。
3. 先测单路已预热的原生流式语音，再测媒体服务器转发。分别报告初始化、预热、首文字、首 PCM、前导静音、有效首音与音频持续时长；少量样本不做稳定性承诺。
4. 对连续打断隔离生成代次，旧语音和工具结果不能恢复播放。已播放内容、被打断的背景、最新用户问题继续区分，不能直接用模型完整生成稿覆盖正式历史。
5. 销售和咨询提示词、一次挽留、明确结束、告别播放后挂断都须回归。全双工模型决定发声，不等于获得自行挂断授权；原有播放屏障和工具校验继续生效。

最初选型阶段仅记录可行性；随后按要求增加独立 MiniCPM-o 4.5 原生半双工流式实验，源码、依赖和语音资产锁定方式见[实验说明](../experiments/openi_latency/README.md#omni-独立实验)。实测结果尚待记录，不修改正式服务。当前三模型优化和 DeepSeek 对照结果见[响应速度文档](latency.md)及[实验记录](../experiments/openi_latency/README.md)。
