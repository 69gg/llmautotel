## 实测基线与边界

2026-11-17 的真实 Chrome 网页测试使用合成语音音轨进入正式 WebRTC；远端 AudioWorklet 以 20ms 窗口检测回复有效 PCM，不包含实体麦克风及扬声器声学延迟。五轮完成回复平均 2094.4ms，范围 1821.3～2314.7ms；GPU 内统计平均 1215.7ms，其中分句与合成平均 800.8ms。另有一轮未回复，随后长连接错误，原因尚未定位。

浏览器与 GPU 两种计时口径平均相差 878.7ms，包含传输、排队、终端缓冲和计时边界差异，尚未逐段隔离，不能全部归为网络。旧的 0.78 秒不是本次复现结果，也不能替代终端统计。移除中继节奏控制也不等于可从首音直接扣除一段音频时长。

## 本次实现

| 环节 | 旧行为 | 新行为与验证 |
| --- | --- | --- |
| 模型线程到异步管线 | 每块结果通过默认线程池等待同步队列；线程池繁忙时，已生成的音频仍可能等待 | 有界异步队列直接唤醒事件循环；保留最多 8 项的背压、错误传播与取消。占满默认线程池时，首块及下一块仍能送达；满队列取消会关闭原推理生成器 |
| GPU 到业务服务器中继 | GPU 按 PCM 时长发送，最终 WebRTC/电话出口再次控制播放节奏 | 仅 GPU 中继使用 `PhoneTransport(pace_audio=False)`，可用音频及时交给最终播放队列；真实电话 provider 仍默认实时发送。测试验证 200ms 已有 PCM 不再在中继处额外播放一遍，但文字仍等待最终播放确认 |
| 播放确认 | 没有新增音频的句末、回复结束等检查点也发送 drain，增加往返 | 记录当前代次已发送及已确认的音频序号；只确认新增音频。新音频、告别和挂断仍等待匹配确认，flush 后重新计数 |
| 发送与打断交错 | `audio-start` 发送期间打断后，旧 PCM 可能被赋予更新后的代次 | 进入发送时固定代次，在锁内及 await 后检查所有权；旧 PCM 不能被标为新回复。可控暂停发送的回归测试复现并验证修复 |

这些改动主要减少线程池依赖、重复限速和无效往返，且修复打断竞态。没有把异步线程切换或两次节奏控制认定为全部 878.7ms 差值的已证实原因。后续仍需关联 GPU 首块、业务服务器收包/出队及浏览器有效音频，才能量化实际节省。

## TTS 选型：保留体量与音色克隆

效果比较需使用同一段干净参考音频及转写，试听口语、金额、型号、停顿、长句和连续插话。下面是待做听感与延迟 A/B 的候选，不代表已经比当前方案更好。

| 方案 | 体量与能力 | 适配判断 |
| --- | --- | --- |
| 当前 Qwen3-TTS 0.6B Base，尝试完整参考上下文克隆 | 模型不变；当前 `xvec_only=True` 只用声纹，完整 ICL 模式需要准确参考转写 | 可先验证克隆韵律是否改善；可能增加 prefill 和首音延迟，不默认切换。锁定的 faster-qwen3-tts 0.5.4 已按参考音频、文本和模式缓存 prompt，不能再把“新增参考缓存”算作本次收益 |
| Fun-CosyVoice3-0.5B-2512 / RL | 约 0.5B，中文及方言、零样本音色克隆，文本与音频双流 | 同体量优先候选；RL 版可一起比较发音准确度与音色相似度。此前普通 PyTorch 路径已有较慢基线，须验证加速实现；上游文本双流与 vLLM 的兼容限制应以所锁版本为准 |
| VoxCPM1.5 | 总体约 0.8B（主干约 0.6B），中英、44.1kHz、参考音频与转写克隆，流式音频输出 | 作为接近体量的另一条听感路线；不能将流式音频输出当作未知文本的双向流输入。当前链路实际输出要求 24kHz，需要真实重采样适配，不能只修改采样率字段 |

不选更大的 Qwen3-TTS 1.7B 或 VoxCPM2 2B 作为本次同体量默认替代。不下载或在本机运行模型。音色、模型、采样率改变时须重新验证打断、播放提交及连续供音。

官方资料：[CosyVoice](https://github.com/FunAudioLLM/CosyVoice)、[VoxCPM](https://github.com/OpenBMB/VoxCPM)、[Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)、[faster-qwen3-tts](https://github.com/andimarafioti/faster-qwen3-tts)。本次已查阅官方说明、Context7 文档和所用 0.5.4 源码缓存实现；官方吞吐或首包宣传不是本项目端到端实测。
