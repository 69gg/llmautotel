# 响应速度测量与流式替换方案

OpenI 自部署选型使用独立的 [三模型延迟原型](../experiments/openi_latency/README.md)，不修改正式模型配置。其合成输入、模拟停口和内存终端与正式电话验收分开报告。

2026-11-15 已完成全站内模型基线：SenseVoiceSmall 整句识别、Qwen3-1.7B 关闭思考、CosyVoice3 双流合成，同机三轮、媒体服务器三轮均成功。有效首音同机 2183.0～3176.9 ms（p50 2714.6 ms），媒体服务器 2864.6～5333.7 ms（p50 3741.8 ms），均未达到 1000 ms。主要等待在 TTS 首块音频路径，不能据此认定换小文本模型即可达标。小样本、模拟停口和内存终端的限制、已停止任务及费用记录见原型文档与[脱敏报告](../experiments/openi_latency/results/2026-11-15-station.json)。

原型新增同一任务中的 TTS 分块复位对照、阶段计时，以及复用正式 DeepSeek HTTP/WS provider 的固定文本测试。vLLM/TensorRT 和文本输入策略均可配置；使用 vLLM 时聚合语义小句进入其支持的入口，不将删除上游断言当作实现双流。命令、准备要求、计费字符预算及单项/整链路口径见[原型说明](../experiments/openi_latency/README.md#tts-优化与接口对照)。配置和单元测试不代表新的 GPU 延迟结果。

2026-11-15 后续 GPU 对照已经完成：恢复 CosyVoice 每段初始分块后，固定完整文本 TTS 有效首音 p50 为 1645.7 ms（原分块 2430.9 ms）；同机完整链路 p50 为 2456.0 ms（本轮原分块 3221.8 ms），媒体服务器转发 p50 为 2812.6 ms。DeepSeek 同文本单项 HTTP/WS 的 p50 分别为 1448.5/1647.5 ms，均未进入 1 秒。各组仅三个样本、测量范围不同，不能当作稳定性或整条链路互相替代的结论。完整数据、初版 HTTP 测量错误及计费记录见[本轮报告](../experiments/openi_latency/results/2026-11-15-tts-compare.json)和[结果说明](../experiments/openi_latency/README.md#2026-11-15-tts-分块与-deepseek-对照)。任务已停止、服务器临时凭据已删除，未修改正式服务。

小型 Omni 作为下一组独立选型，优先核查 MiniCPM-o 4.5 的原生流式语音和可配提示词，再用 Qwen2.5-Omni-3B 对照；硬件、接口限制和验收边界见 [Omni 选型](omni-evaluation.md)。本轮没有部署或测量 Omni，官方首 token/每单元数据不等于停口至有效首音。

最终验收口径为“用户实际停口 → 终端第一段有意义的回复语音”，目标不超过 1000 ms。占位话、静音、开场首音和服务端页面指标都不能替代这个口径。首句内容也要人工核对确实在回答最新问题。

## 已实现

销售口语风格使用短句、自然承接和相关步骤推进。身份、产品、活动、价格、位置和销售步骤均来自配置；不根据产品名分支，也不虚构优惠或历史联系。保留咨询模式、直接推销旧版、各电话 provider、一次挽留、打断背景和告别播放后挂断。

`voice.response_chunking=first_clause` 允许首段中文分句提前合成；`sentence` 使用旧版整句路径。最少字数、停口确认和目标可在页面配置。新空配置停口默认 0.3 秒，已有显式值保留。TTS 表达要求由所选协议发送；留空保持原请求。DeepSeek 已有关闭思考配置保留，不发送 token 上限。

本机媒体管线通过官方 Pipecat 观察器记录服务端首音与阶段耗时。页面展示的是服务端输出，未扣除音频前导静音，也不包含真实网络终端的缓冲和设备播放。云托管语音缺少本机音频事件时不伪造指标。

## 可复测基准

```sh
uv run python -m llmautotel.benchmark \
  --question '支持哪些功能？' --samples 3 \
  --chunking first_clause --vad-stop 0.3
```

脚本以只读方式打开 `LLMAUTOTEL_DATA_DIR` 指定的数据库，也可传 `--data-dir`。使用配置的 TTS 在内存准备问题；完整播放当前配置开场后，将测试问题按 20 ms 实时采集节奏送入原生媒体管线，再经历 VAD、真实 ASR、文本模型、TTS 和输出队列。开场不计为回复样本，准备问题的合成耗时不计入回复延迟。每个样本创建独立会话；模型 HTTP 连接可能已由开场预热。

有效 PCM 采用 20 ms 块的 RMS 幅度判断，默认阈值 300，可用 `--threshold` 调整。输入尾部低于阈值的块剔除，最后有效输入块结束作为停口时刻；输出同样跳过低幅度块，时间精度约 20 ms。这是本机内存终端测量，不能证明耳机、外放或电话已达到 1 秒。短语中的自然停顿可能被拆回合；多回合、无有效文字、无有效音频或提前回复的样本会失败，不算达标。

脚本输出识别文字、回复文字、有效 PCM 延迟及服务端阶段；需人工检查首句语义。`--chunking sentence` 可对照旧路径；仅传入的阈值覆盖本次快照，不保存配置。退出码 0 为本轮内存样本都不超过参照，1 为至少一个超出，2 为测量未完成；失败不打印上游正文或凭据。不连接真实电话、不获取麦克风、不写历史、不保存音频，也不修改任何线路开关。每个样本包括开场和回复的超时可通过 `--timeout` 指定，默认 90 秒。

## 2026-11-14 的真实接口结果

从受限本机配置读取当前 MiMo ASR/TTS 和 DeepSeek 文本模型。TTS 能合成中文问题和开场；两次完整链路尝试未产生有效回复样本。拆开协议确认：MiMo ASR 与 DeepSeek 文本模型均返回 **HTTP 402**。未依据状态码猜测具体余额、套餐或权限原因，也未修改凭据、服务地址或模型。须由账户方恢复对应接口后复测。

同一 MiMo TTS 客户端连续合成“目前支持整理资料和辅助编写。”，三次从请求到首块 PCM 分别为 **1127.7、1831.6、621.5 ms**，每次返回 138240 字节、24 kHz 单声道 PCM。这里只统计接口首块，不是终端有效声音；2/3 的请求仅合成等待就超过 1 秒，不能保证现有组合稳定满足总目标。三次小样本不构成分位数或服务承诺。

本轮未获得完整 ASR → LLM → TTS 的成功样本，不能宣称达到 1 秒，也不沿用旧测试值作为当前结果。按用户要求跳过浏览器实际验收；耳机、外放、运营商线路和参考录音的现场听感对齐均未验收。

## 后续流式方案

当前分段 HTTP ASR 在停口后才上传整段音频；TTS 虽输出流式音频，每个请求仍等待一个文本分句。仅降低停口阈值和缩短提示词不足以保证总延迟。可在保留 `openai` / `mimo` 旧接口的前提下，增加独立实时协议，并逐项实测后选择。

| 环节 | 候选与工作方式 | 需要验证 |
| --- | --- | --- |
| 实时 ASR | 阿里百炼 Fun-ASR-Realtime 或 Paraformer，通过 WebSocket 边讲话边上传，区分中间和最终识别 | 地域、模型权限、16 kHz PCM、final 与 VAD 的回合衔接、停口后的实际 final 延迟 |
| 双流 TTS | CosyVoice WebSocket，持续发送文本事件，服务端同时返回音频；复用连接处理多个任务 | 音色/语气、采样率、首段边界、首包前导静音、取消和迟到音频隔离 |
| 文本模型 | 保留现有关闭思考的流式 LLM；恢复后先测首段有效答案耗时 | 包含工具与完整提示词的首段延迟，不能仅测一句问候 |
| 媒体与验收 | 沿用原生打断、队列清理和终端播放屏障；分别测网页与甲方实际线路 | 连续插话、回声、网络抖动、告别完整播放、多个短句和长句的 p50/p95 |

实时 ASR 不能只换 URL：需将最终结果与当前输入片段关联，替换分段 HTTP 专用的最终转写屏障，防止旧 final 结束新回合。双流 TTS 的任务也需绑定当前生成代次，打断后取消旧任务并清空音频；不能复活旧回复或提前提交未播放背景。新增协议应默认关闭，旧配置继续可用。

这些是已查证协议能力后的替换方案，本轮未添加未验证的新 provider，也未提供新服务的凭据或真实线路测试结果。供应商的单阶段延迟宣传不等于本项目整条链路达标。

官方资料：[Fun-ASR-Realtime](https://help.aliyun.com/zh/model-studio/fun-asr-real-time-speech-recognition-api-reference)、[Paraformer](https://help.aliyun.com/zh/model-studio/paraformer-real-time-speech-recognition-api-reference)、[CosyVoice WebSocket](https://help.aliyun.com/zh/model-studio/cosyvoice-websocket-api)。

## DeepSeek 流式语音接入

DeepSeek TTS 现已支持 WebSocket 双向流式输入：在整句尚未生成完成时开始请求并接收音频。`tts.protocol=deepseek` 默认启用，`streaming_input=false` 可回退 HTTP 分句；基准与真实通话使用同一工厂选择协议。两条路径都按真实 PCM 统计，不使用占位话。

DeepSeek ASR 官方不支持流式识别，仍需用户停口后上传完整 WAV。这能减少 TTS 侧等待，但无法消除 ASR、LLM、网络和设备延迟；没有成功的完整链路及终端测量前，1 秒目标仍未验收。配置与检查点边界见 [DeepSeek 语音](deepseek-audio.md)。

本轮新工具真实复测：DeepSeek WebSocket TTS、HTTP TTS 和 ASR 均为 HTTP 402，没有可报告的成功首音或完整回复延迟；ASR 静音探测不代表识别准确率测试。与前节 MiMo 单项结果分开记录，不用旧结果替代新接口验收。
